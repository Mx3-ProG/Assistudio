# V0.9 — Partner payout requests

A partner with an available balance asks for a payout in one click; Studio ATS
validates and pays it (manually in V1), and the partner follows each step.

```
sale → commission pending (validation) → available → REQUESTED → PROCESSING → PAID
                                                    ↘ REJECTED (reason) / FAILED → cents available again
```

## What existed and was reused

| Piece | Before | Now |
|---|---|---|
| `payouts` (PAY-XXXXXX, method, provider ref, Stripe transfer id) | staff-created only | also the partner's request (`status = requested`) |
| `staff_create_payout` / `staff_mark_payout_paid` | whole balance, `commissions.payout_id` | same API, now on allocations |
| `commission_ledger`, `ledger_settlements` | append-only, clawbacks netted | unchanged; partial payouts write `payout` entries per allocation |
| Stripe Connect (Express onboarding, `account.updated`) | prepared, disabled | unchanged + last 4 digits for display |
| Email outbox → Resend | transactional emails | 3 new templates |
| `affiliate_balances` view | requested money still "available" | `available` net of requests, new `requested_cents`, partial payouts in `paid` |

## Data (migrations `20261012000001/2`)

- `payout_status` + `requested`, `rejected`; `notification_type` + `payout_request`.
- `payouts` + `requested_by`, `balance_before_cents`, `processed_at`, `rejected_at`, `failed_at`,
  `rejection_reason`, `admin_note`, `stripe_account_id`, `idempotency_key`.
  Payment reference = existing `provider_ref`.
- `payout_allocations(payout_id, commission_id, amount_cents, released_at)` — which cents of which
  commission belong to which payout. Partial requests split a commission (FIFO, oldest first).
- `payout_events` — append-only history (who, from → to, amount, note) + `audit_logs`.
- `affiliates.connect_payout_last4` (display only).
- Commission statuses unchanged: "payout requested" is derived from live allocations.

## Guarantees (all server-side, in SQL `SECURITY DEFINER` functions)

- Identity from `auth.uid()` only; the amount sent by the browser is a wish.
- Minimum (`payout.minimum_cents`, 50 €), amount ≤ payable balance, approved partner.
- One open payout per partner: affiliate row lock + unique partial index `payouts_one_open_idx`.
- Idempotency key per dialog opening: a double click returns the same request.
- A commission can never be allocated beyond its amount; a refunded / disputed commission blocks
  processing and payment (`payout_problem`) until staff reject the request.
- Refund after a partial payout: paid cents are clawed back, unpaid cents reversed.
- Partners cannot write `payouts`, allocations or events, nor call staff functions; RLS limits reads to
  their own rows. Staff actions check `is_staff()`.

Tests: `supabase/tests/payout_requests_test.sql` (73 assertions), `src/lib/payouts.test.ts`,
email rendering in `src/lib/email/templates.test.ts`.

## Screens

- Partner: `/dashboard/payouts` — available amount + [Request my payout], 5 counters, request in
  progress on its path, payout method, requests, money history.
- Admin: `/admin/payouts` (filters) and `/admin/payouts/[id]` (commissions, history, actions with
  confirmation; paying needs the transfer reference, rejecting / failing a reason).

## Emails

`affiliate.payout_requested` (partner), `staff.payout_request` (every admin, CTA to the request),
`affiliate.payout_rejected`; existing `affiliate.payout_sent` when paid. A failed email never blocks
the request (outbox, retried by the cron).

## Stripe Connect — next step

Already in place: connected account id, onboarding status, `payouts_enabled`, method `stripe_connect`
snapshotted on the request with the account id, `stripe_transfer_id` column.
To automate: on `staff_process_payout` for `method = stripe_connect`, create a Stripe transfer to
`stripe_account_id` (idempotency key = payout id), store `stripe_transfer_id`; handle
`transfer.reversed` / payout failures by calling `staff_fail_payout`, success by
`staff_mark_payout_paid(provider_ref = transfer id)` from the webhook (service role variant).
