# STUDIO V0.2 — Payments, attribution, recurring commissions, emails

```
Affiliate → /s/{code} (click + server-side touch) → Visitor → Lead → /buy
  → Stripe Checkout (created server-side) → payment → signed webhook
  → invoice + payment + sale (1 per paid invoice) → commission engine
  → commission `pending` + ledger entry + activity + notification + email (outbox)
  → validation period (cron) → `available` → payout (staff, audited)
  → next year: Stripe renews → new invoice → renewal sale → new commission
```

**Sources of truth.** Stripe (via signed webhooks) for every financial fact. Supabase for identity, attribution, commissions, ledger, statuses, history. `/success` never records anything: it polls a read-only status endpoint.

## Commission statuses

| Status | Meaning | Counted as earned? |
| --- | --- | --- |
| `pending` | Stripe confirmed the payment; validation period running | **No** |
| `disputed` | Needs an administrative decision (dispute, partial refund, self-referral, non-approved affiliate) | **No** |
| `available` | Validated, payable | Yes |
| `paid` | Included in a paid payout | Yes |
| `reversed` | Refund / chargeback / manual reversal. Paid ones create a `clawback` (negative, recovered from the next payout) | — |
| `awaiting_payment` | Legacy V0.1 manual sale not yet paid. Never created by V0.2 | No |

A commission is **created only when its payment is confirmed**. Renewal commissions are created by the renewal payment itself (`renewal_commission` ledger entry) — nothing is generated in advance. Recurring book and "potential next 12 months" are projections computed by `project_next_commission()` under today's rules, and labelled as such.

## Idempotency & concurrency

1. `stripe_events.stripe_event_id` UNIQUE + `stripe_event_claim()` (atomic claim, 5-minute stale lock, retry of failed events).
2. One transaction per financial fact (`stripe_invoice_paid`, `stripe_refund_sync`, …) with an advisory lock per Stripe object.
3. Business keys: `sales.invoice_id` UNIQUE, `commissions (sale_id, affiliate_id)` UNIQUE, `refunds.stripe_refund_id` + `applied_at`, `disputes.stripe_dispute_id`, `email_events.idempotency_key`.
4. Emails are committed in the same transaction as the fact (outbox) and sent after commit with a Resend `Idempotency-Key`.

## Local development (Stripe test mode)

```bash
cp .env.example .env.local          # Supabase project + Stripe TEST keys + Resend key
npm run db:push                      # applies supabase/migrations
STRIPE_SECRET_KEY=sk_test_… npm run stripe:setup   # creates STUDIO + €6,000/year price (lookup key studio_yearly_eur)
npm run stripe:listen                # Stripe CLI → prints whsec_… → STRIPE_WEBHOOK_SECRET

```

Buy with test card `4242 4242 4242 4242`. To test a renewal: `stripe trigger` cannot renew an existing subscription; use a **test clock** (Dashboard → Billing → Test clocks) and advance it one year. Failed renewal: attach `4000 0000 0000 0341` then advance the clock.

**Webhook endpoint** `https://<site>/api/webhooks/stripe` — events to enable:
`checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`, `customer.subscription.created|updated|deleted|paused|resumed`, `invoice.paid`, `invoice.payment_failed`, `charge.refunded`, `refund.created|updated|failed`, `charge.dispute.created|updated|closed`. Connect endpoint (optional, own secret in `STRIPE_CONNECT_WEBHOOK_SECRET`): `account.updated`.

## Who sends which email

| Communication | Sender | Why |
| --- | --- | --- |
| Receipts, invoices, card-update / dunning emails, upcoming renewal reminders | **Stripe** (enable in Stripe Billing settings) | Legal documents + payment links live at Stripe; no duplication |
| Welcome to STUDIO (after confirmed payment), cancellation confirmation, lead confirmation, appointment confirmation | **STUDIO / Resend** | Business relationship, not billing |
| Order confirmation, renewal receipt, failed payment | Templates exist; sent by STUDIO **only** if `emails.customer_billing_owner = studio` | Avoid double emails |
| Affiliate: welcome, new lead, appointment, sale detected (pending!), commission available, payout sent, renewal, customer cancelled | **STUDIO / Resend** | Nobody else knows about affiliates |

## Decisions still to confirm (conservative defaults in place)

| Topic | Current default | Setting / place |
| --- | --- | --- |
| Validation period | 30 days (V0.1) | `commission.validation_days`, or per rule |
| Attribution | last click, 90 days (V0.1) | `attribution.model`, `attribution.window_days` |
| Commission base | amount **excluding tax** | `commission_rules.base` |
| Partial refund | commission → `disputed` for manual review | `refund.partial_policy` |
| Clawback of a paid commission | negative balance recovered from next payouts | engine |
| Renewal commissions | every eligible renewal, no end date | `commission_rules.duration_months` / `max_payments` |
| Payout minimum / cadence | €50, monthly label only (payouts are created by staff) | `payout.minimum_cents`, `payout.schedule` |

| Proration / manual invoices | revenue recorded, commission needs review | engine (`billing_reason_requires_review`) |
| VAT / Stripe Tax, promo codes, customer portal | not enabled | Stripe configuration |

## Security notes

- Secrets are only read in server-only modules (`import "server-only"`); the production client bundle was scanned for secret names: none.
- Webhook: raw body, signature verified against every configured endpoint secret, 5-minute tolerance, 400 on bad signature, event livemode must match the key mode.
- Checkout: price and attribution resolved server-side; Stripe metadata only points back to our `checkout_sessions` row, whose Stripe ids are re-checked by the webhook (`checkout_session_mismatch`). A Stripe price that differs from the configured offer blocks checkout.
- All service functions are revoked from `anon`/`authenticated`; staff functions check `is_staff()` and require a reason; affiliates cannot change Connect / payout fields (guard trigger) nor rewrite notifications (column grants).
- Logs are JSON with key-based redaction (emails, names, addresses, secrets, card/bank fields).
